The Homelab, Ten Months In

Aug 15, 2026 · 11 min read · #kubernetes #homelab #networking #automation #security

share xin

OverviewHardwareThe stackThe MacBook sagaDisaster recoveryConclusion
01Overview

If you read my k3s homelab post, you met this cluster back when it was one secondhand MacBook Pro and a k3s install. That post is basically a baby photo at this point :) Ten months later it's a 5-node Talos Linux cluster, ~33 ArgoCD-managed apps, disaster recovery split across two cloud providers, and a full observability stack.

The one rule that hasn't changed, straight from the repo's README: "Everything is in this repo - if it's not here, it doesn't exist on the cluster." ArgoCD reconciles main against the live cluster. The only thing applied by hand is the bootstrap step that installs ArgoCD itself.

02Hardware
  • Control plane (cp0): still the same 2012 MacBook Pro! 13", Intel i5, upgraded to 16GB DDR3. Survived two full cluster rebuilds (k3s → kubeadm → Talos). This laptop will not quit.
  • Workers (wrk0-wrk3): four Lenovo M920q Tiny boxes, 16-32GB DDR4, NVMe. Each exposes its iGPU via Talos's i915 extension for hardware transcoding.
  • GPU node: a gaming PC, Ryzen 7 7800X3D, RTX 4070 Ti Super. Joins the cluster on-demand, tainted gpu=nvidia. Way too expensive to leave running 24/7.
$ kubectl get nodes -owide
NAME   STATUS   ROLES           VERSION   OS-IMAGE
cp0    Ready    control-plane   v1.36.2   Talos (v1.13.1-custom)
wrk0   Ready    worker          v1.36.2   Talos (v1.13.1)
wrk1   Ready    worker          v1.36.2   Talos (v1.13.1)
wrk2   Ready    worker          v1.36.2   Talos (v1.13.1)
wrk3   Ready    worker          v1.36.2   Talos (v1.13.1)
03The stack
  • OS/K8s: Talos Linux, Kubernetes v1.36.2
  • Networking: Cilium as the CNI, Gateway API, no NGINX Ingress needed
  • Storage/DB: Longhorn for storage, CloudNativePG for Postgres
  • GitOps: ArgoCD, obviously. Secrets: Sealed Secrets + SOPS
  • Metrics/logs: kube-prometheus-stack + Thanos + Loki, plus Kepler for power draw priced in SAR

Why Talos instead of a regular distro plus kubeadm? No SSH surface to harden, API-managed end to end, fits the "everything through the repo" idea all the way down to the OS. It also, as it turns out, does not fit an EFI Mac out of the box. Which brings me to the best story in this whole project.

04The MacBook Pro vs. Talos Linux saga

Fully written up in the repo docs, but here's the short version: three separate, unrelated firmware bugs, stacked on top of each other, on the same 14-year-old laptop. Seriously.

Bug 1: Talos 1.13+ switched their kernel build to Clang+LLD, and Apple's EFI firmware just rejects the resulting binary outright. Machine hangs at the boot logo, ZERO kernel output. For the control plane I rebuilt the Talos kernel from source, stripping LLVM: 1 out of the build config so it compiles with GNU ld instead.

Bug 2 was systemd-stub's status line freezing inside systemd-boot itself, before the kernel even got a chance to run. Fix: swap it for GRUB, which Talos only lets you pick through the imager's disk-image build mode. Bug 3, a bonus: Talos's GRUB build hardcodes (hd0,gpt3)/grub, and this Mac's firmware enumerated the internal disk as hd1. Of course it did.

End result: a fully custom Talos image running as the control plane of a Kubernetes cluster, on a 14-year-old laptop, and it survives unattended reboots now. Still super proud of this one.

05Disaster recovery, for real this time

I went auditing my backups a while back and found Velero had been silently failing 100% of the time, thanks to a bug in velero-plugin-for-gcp:v1.13.0. Fixed by bumping the version, and this time I actually verified it end-to-end instead of trusting a green checkmark.

Same audit, second surprise: Longhorn's own backup target was pointing at nothing. I stood up a whole new AWS account and bucket just for this, so the two backups can't die together. A daily job now backs up every volume with 14-day retention, and I actually tested a restore. Once bitten, twice shy!

06Conclusion

Going from a 2GB MacBook running k3s to a fully GitOps'd, disaster-recovered, actually-observable cluster took about ten months and a genuinely stupid amount of firmware debugging. But honestly, what sticks with me is that the boring stuff mattered most: verifying backups actually restore, mapping traffic before writing a deny policy, rotating a credential the second I know it leaked. It's the difference between a homelab and a homelab you can actually trust.
